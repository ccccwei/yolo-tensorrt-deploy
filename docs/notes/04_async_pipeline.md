# 04：双缓冲异步流水线

01 做完一张图片的 CPU 前处理、上传、GPU 推理、下载和 CPU 后处理后，才开始下一张。04 希望在第一张图片还没返回时，就为第二张安排工作，让 CPU 准备数据与 GPU 执行有机会重叠。它主要研究吞吐量，同时记录每张图片实际等待了多久。

源码：[main.cpp](../../src/04_async_pipeline/main.cpp)、[preprocess.cu](../../src/04_async_pipeline/preprocess.cu)。基准实现见 [01 源码](../../src/01_baseline/main.cpp)。

## 从等待一张图，到容纳两张图

假设依次处理 A、B、C 三张图片。01 只有一套正在使用的输入输出：A 完成前，不能拿同一块输入去装 B，否则 GPU 可能读到被覆盖的数据。因此，直接删掉等待语句并不能得到正确的并发程序。

04 准备两套互不覆盖的工作区：先把 A 放进第一套，再把 B 放进第二套；第一套的 A 完成并取走结果后，才放入 C。每套工作区称为一个**槽（Slot）**。默认使用两个槽，也就是双缓冲。

```text
提交槽 0 的 A
提交槽 1 的 B
等待并处理 A 的结果 → 槽 0 提交 C
等待并处理 B 的结果 → 槽 1 提交下一张
最后取完仍在槽里的结果
```

这里同时在途的是两个独立请求，每次模型推理的 batch 仍为 1。两个请求是否真的在 GPU 上重叠、重叠多少，还取决于 GPU 的执行资源和传输能力。

## 相对 01，单个请求也发生了变化

为了让两套工作区适合异步传输，04 不再在 CPU 上生成浮点模型输入。它把普通原图先复制到本槽的锁页内存，再上传，由 CUDA 生成 TensorRT 输入。

锁页内存仍是 CPU 内存，但使用期间相关内存页不会被换出，适合设备异步传输。这个专门准备的输入暂存区要逐请求复制，复制成本也计入延迟。

CUDA 前处理同样承担完整的输入转换。例如 1280 × 720 图片进入 640 × 640 模型时，先缩为 640 × 360，再上下各补 140 行；GPU 线程计算采样位置、做双线性插值与舍入，将 BGR 改为 RGB、除以 255，写入三个连续通道平面。它直接生成模型输入，避免保存多张中间图。

```text
01 单请求：CPU 前处理 → H2D → TensorRT → D2H → 等待 → CPU 后处理
04 单请求：CPU 复制到锁页区 → 原图 H2D → CUDA 前处理
          → TensorRT → 锁页输出 D2H → 等待结果 → CPU 后处理
```

H2D 是主机到显存的复制，D2H 是返回主机的复制。模型权重和 CPU 后处理规则保持不变；相对 01，04 同时引入 CUDA 前处理、锁页缓冲区、独立的两套执行资源和跨请求调度，不能把总加速比只归因于双缓冲。

## 每个槽为什么需要独立资源

两张图的中间结果不能互相覆盖，所以每个槽都拥有自己的原图显存、模型输入、模型输出，以及主机侧的锁页输入输出缓冲区。图像编号、任务序号、缩放比例和补边位置也随槽保存，否则 B 的框可能按 A 的尺寸恢复坐标。

TensorRT engine 保存网络与权重，两个槽共享它；**execution context** 保存执行所需的状态，各槽独占一个。并发执行时不能让两个槽共用同一个 context。

每槽还有一条 **CUDA stream**，即 GPU 工作的有序队列。`prepare_slot()` 创建 non-blocking stream，避免与默认 stream 发生隐式同步；同一槽内的任务仍按顺序执行，所以推理一定在前处理完成后读取输入，D2H 一定在推理完成后读取输出。

为了知道何时可以取回结果，程序在每条 stream 的 GPU 工作前后放置两个 **event**，也就是队列中的时间标记。`done_event` 到达时，说明本槽的上传、前处理、推理和下载都已完成。

初始化时，所有图片先解码到普通内存，槽的原图缓冲区按最大图片预分配。正式测量期间复用 context、events、锁页内存和显存，避免边运行边扩容；代价是两套执行资源和全部原图都会占用内存。

## 提交与取结果要分开

`submit()` 先把本张原图复制到槽内锁页区，然后连续提交 GPU 工作：

```text
start event → H2D → CUDA 前处理 → TensorRT → D2H → done event
```

提交后，CPU 不在每个 GPU 阶段后等待，而是可以继续准备另一槽。这种提交工作后继续向前执行的方式称为**异步**；数据正确性由槽的独占资源和 stream 的执行顺序保证。

`finish()` 则先等待 `done_event`，再读取锁页输出做 CPU 后处理。输出为 `[1,300,6]` 的候选框，CPU 检查有限值、过滤低于 0.25 的分数，按本图缩放和补边信息还原坐标，裁剪边界并去掉无面积框。只有这些工作完成后，槽才变为空闲。

`run()` 总在复用槽之前调用 `finish()`，循环结束后按提交顺序取完剩余结果，这个收尾过程叫 **drain**。即使只提交一张图、还没填满两个槽，也必须完成收尾，否则最后一张图可能没有结果。

预热也走同样的提交与收尾流程。预热结束时先清空在途请求，正式测量从空槽开始。异常退出时，`Slots` 先等待全部 stream，随后各槽销毁 context、events 和缓冲区，最后才释放共享 engine。

## 为什么完成得更多，不等于每张更早返回

想象两个请求发生了重叠：它们占用 GPU 的总时间可能短于逐张执行，但第二个请求仍要等待部分资源，第一个请求也可能受到竞争影响。因此，单位时间完成的图片数可以增加，而每张图片从提交到拿到结果的时间也可能增加。

`timings.csv` 的 `total_ms` 从本请求开始复制到锁页区计时，直到 CPU 后处理完成。它包含入槽后的 GPU 排队、资源竞争和等待结果被消费的时间，不含尚未取得槽之前的上游排队。

`staging_ms` 只测 CPU 暂存拷贝；`gpu_ms` 用两个 event 测量上传、CUDA 前处理、TensorRT 和下载的区间；`postprocess_ms` 测 CPU 处理输出。不同字段的边界并不拼成完整请求，不能要求前三列相加恰好等于 `total_ms`。

吞吐量在独立的 `throughput.csv` 中记录：

```text
FPS = 正式完成的样本数 × 1000 / 正式测量的总墙钟毫秒数
```

这段总时间包含填充流水线、提交、等待、CPU 后处理、内存中的统计记录与最终 drain，不含初始化、解码、预热、绘图和文件写入。请求可以重叠，**不能用 `1000 / P50` 代替实测 FPS**。

## 相对 01 的结果

统一实验使用 RTX 3060、YOLO26m FP16 / FP32 I/O、640 × 640、batch 1、Release；`bus.jpg` 和 `zidane.jpg` 共 3 轮，每轮每图预热 200 次、测量 1000 次，每版 6000 条请求记录。

| 版本 | 请求 P50（ms） | 相对 01 加速比 |
| --- | ---: | ---: |
| 01 · CPU 前后处理、逐张执行 | 4.547317 | 1.00× |
| 04 · CUDA 前处理、锁页缓冲、双槽 | 6.330046 | **0.72×** |

`4.547317 ÷ 6.330046 ≈ 0.72`，表示本轮默认双槽 04 的请求 P50 比 01 高约 39.2%，单张请求返回更慢。这是完整请求的比较，既包含前处理和内存路径变化，也包含双槽执行等待，不能只归因于双缓冲。

本表没有给出相对 01 的吞吐倍率：统一对照汇总的是请求 P50，01 没有配套的整段吞吐计时。不能拿 01 的 P50 倒数补出吞吐基准。[统一测试报告](../benchmarks/rtx3060-yolo26m-2026-10-15/README.md)保留逐轮结果和环境；结论限于本轮两张示例图的重复测试。

## 自己运行一次

先按仓库 README 准备依赖与 engine，然后在仓库根目录执行：

```bash
cmake --preset release -DCMAKE_CUDA_ARCHITECTURES=native
cmake --build --preset release --target yolo_baseline yolo_async_pipeline -j
./build/release/src/yolo_baseline weights/yolo26m.fp16.engine images 1000 200
./build/release/src/yolo_async_pipeline weights/yolo26m.fp16.engine images 1000 200 2
```

两版用同一 engine、图片和次数，结果分别写到 `results/01_baseline/` 和 `results/04_async_pipeline/`。重复运行会覆盖同名输出，多轮比较时先另存目录。上面用于本地对照，已记录结果的 engine 哈希见统一报告。

本篇内部还可以将最后一个参数改为 `1`，只保留一个槽；这不会把程序变回 01，因为 CUDA 前处理、锁页缓冲区和本版计时方式仍在：

```bash
./build/release/src/yolo_async_pipeline weights/yolo26m.fp16.engine images 1000 200 1
```

读代码时沿着 `prepare_slot()` → `submit()` → `finish()` → `run()` 跟踪即可。如果单张推理已经占满 GPU，增加槽数可能主要增加竞争与等待；双槽也会占用更多显存、锁页内存和 TensorRT 执行内存。

一个具体练习是用三张不同尺寸的图片运行双槽，并核对每张图的结果与计时行数。第三张图片会复用第一张的槽，能帮助检查：槽被复用时，旧请求是否完成、尺寸和图像编号是否正确更新。
