# 11：检测头里的 Grouped TopK

01 的一次请求是“CPU 前处理 → 上传输入 → TensorRT 推理 → 下载输出 → CPU 后处理”。这条路径中，模型执行不仅包括卷积等特征计算，还包括从候选结果里挑出高分项。

本篇从这次挑选出发：保持训练好的权重不变，重新组织模型内部的选择过程。理解下面的例子只需要数组、索引和大小比较；不需要先读其他优化篇。

## 先从八个数里选出四个

假设数组是 `[99, 98, 97, 96, 4, 3, 2, 1]`，任务是返回最大的四个数及其原始位置。直接在整个数组上挑选，就是 TopK：K 表示要保留的数量。

现在把数组分成前后两组。如果每组只保留两个，再拼成四个，结果会变成 `[99, 98, 4, 3]`，漏掉 97 和 96。因为所有赢家可能集中在同一组，不能把最终名额平均分给各组。

正确做法是每组最多保留 K 个候选，再从合并后的候选里取一次 TopK。本例每组都保留四个，第二次选择仍得到 `[99, 98, 97, 96]`。小数组没有节省工作，但它说明了分组必须遵守的规则。

为什么局部筛选不会丢掉必要的高分项？如果某个数连本组前 K 都进不了，本组已经至少有 K 个不小于它的数。把所有组放在一起时，这个数也不是获得全局前 K 个分数所必需的。这个过程叫 **Grouped TopK（分组选择）**。

## 把过程对应到 YOLO26m

当前模型先从 8400 个位置中选出 300 个位置，再从这 300 个位置的 80 类分数中选出 300 个预测。这里的两个 TopK 都在 engine 内部，发生在输出 `[1,300,6]` 之前；它们与 01 在 CPU 上做的置信度过滤不是同一步。

| 选择任务 | 原始输入 | 分成 8 组后的执行过程 |
| --- | --- | --- |
| 选位置 | 8400 个位置分数 | 每组 1050 选 300，再从 2400 个候选中选 300 |
| 选预测 | 300 × 80 = 24000 个分数 | 每组 3000 选 300，再从 2400 个候选中选 300 |

每组仍保留 300 个，而不是保留 `300 / 8` 个。较小的选择任务可能更适合 GPU 的执行方式，但它增加了分组、合并和索引处理；是否更快，要看 TensorRT 最终生成的执行计划。

分组还改变了索引的含义。以第二次筛选为例，每组长度是 3000；若合并后的赢家指向“候选数组第 650 项”，它属于第 `650 / 300 = 2` 组。取回该项保存的组内原始索引，比如 17，才得到真正的原始位置：

```text
原始位置 = 组号 × 每组长度 + 组内原始索引
         = 2 × 3000 + 17
         = 6017
```

组号从 0 开始，除法取整数部分。[grouped_nodes()](../../tools/grouped_topk.py) 用 `Reshape` 改变数组视图，用两级 `TopK` 选分数，再用 `GatherElements` 取回组内索引并加上组偏移。这里的图指 **ONNX 模型图**：节点描述模型要执行哪些算子。

## 相对 01，本篇方案还改变了哪些步骤

模型输入输出接口保持 FP32 `images [1,3,640,640] → output0 [1,300,6]`，因此 01 也能读取改写后构建的 engine。本篇不增加第 11 个 C++ 程序；统一性能测试使用现有的 `yolo_registered_input` 执行改写后的模型。

这条运行路径需要在本篇内说明清楚。01 在 CPU 上制作完整的 RGB 浮点输入；本篇测试路径先把原始 BGR 图片上传到 GPU，让 GPU 完成缩放、补边、颜色排列和归一化。为了让传输直接使用原图的主机内存，程序提前用 `cudaHostRegister` 注册这块内存，并保持它的地址有效，直至 GPU 完成访问后再注销。这省去的是额外的 CPU 暂存复制，上传图片的 H2D 仍然存在。

上传、GPU 前处理、模型执行和输出下载，每次都按同一顺序发生。程序把这条工作链记录一次，再重复提交这份记录，这叫 **CUDA Graph**。它记录 GPU 任务的执行关系；前面的 ONNX 图描述模型算子，两者修改的是不同层面。

```text
01：CPU 前处理 → 上传浮点输入 → 原模型 → 下载 → CPU 后处理
11：注册原图 → [上传像素 → GPU 前处理 → 分组模型 → 下载] → CPU 后处理
                方括号内由 CUDA Graph 重放
```

注册和 Graph 创建放在每张图片的准备阶段，正式迭代复用这些资源。01 的 CPU 后处理规则仍保留。因此下文相对 01 的加速比包含了输入处理、内存使用、任务提交和模型改写的共同效果，不能全部算作 TopK 的贡献。

## 相对 01 的实测结果

| 版本 | 请求 P50（ms） | 相对 01 加速比 |
| --- | ---: | ---: |
| 01 原模型、CPU 前后处理 | 4.547317 | 1.00× |
| 11 注册输入 + Grouped TopK | 3.484134 | 1.31× |

加速比为 `4.547317 / 3.484134`；本次完整方案的请求中位延迟降低约 23.4%。该倍率包含运行路径和模型改写的共同效果；单独与 09 的 3.519440 ms 相比仅降低约 1.0%，尚不能证明 TopK 的稳定收益。

数据来自 2026-10-15 的统一测量：RTX 3060、YOLO26m FP16 / FP32 I/O、640 × 640、batch 1、Release；两张图，3 轮，每轮每图预热 200 次、测量 1000 次，每版 6000 个样本。01 使用原模型 engine，11 使用配对的分组 engine；P50 从全部请求样本合并计算。[统一报告、engine 哈希与原始数据](../benchmarks/rtx3060-yolo26m-2026-10-15/README.md)。

请求时间包含每轮 H2D、GPU 前处理、推理、D2H 和 CPU 后处理，排除解码、注册、Graph 创建、预热、注销和结果保存。若每张图只用一次，准备阶段的开销也需要计入实际成本。

## 从原模型生成新文件并运行

先按[项目首页](../../README.zh-CN.md#快速开始)准备导出环境和 `weights/yolo26m.onnx`。以下命令在仓库根目录执行；`topk-g1` 保留原图，`topk-g8` 分成八组。输出 ONNX 必须使用尚不存在的路径，脚本拒绝覆盖已有文件或符号链接。

```bash
.venv-export/bin/python tools/grouped_topk.py \
  weights/yolo26m.onnx weights/yolo26m.topk-g1.onnx --groups 1
.venv-export/bin/python tools/grouped_topk.py \
  weights/yolo26m.onnx weights/yolo26m.topk-g8.onnx --groups 8

sh tools/build_engine.sh weights/yolo26m.topk-g1.onnx
sh tools/build_engine.sh weights/yolo26m.topk-g8.onnx

cmake --preset release -DCMAKE_CUDA_ARCHITECTURES=native
cmake --build --preset release --target yolo_baseline yolo_registered_input -j4

# 01 基准：原模型与 CPU 前后处理。
./build/release/src/yolo_baseline weights/yolo26m.topk-g1.fp16.engine images 1000 200
# 本篇方案：分组模型与注册输入路径。
./build/release/src/yolo_registered_input weights/yolo26m.topk-g8.fp16.engine images 1000 200 1
```

两条命令分别写入 `results/01_baseline/` 和 `results/09_registered_input/`，重复运行会覆盖同名文件。本篇复用的程序参数为 `ENGINE IMAGE_FOLDER [ITERATIONS=200] [WARMUP=50] [REGISTERED=1]`；最后的 `1` 启用注册原图，Graph 始终启用。上面的命令用于在自己的环境重跑流程；重新构建的 engine 不一定复现表中数值。

如果要单独检查模型改写的作用，固定 `yolo_registered_input`、图片、参数和所有运行时步骤，只把 engine 换成 `topk-g1` 与 `topk-g8`，另存两份结果。构建也要控制变量：两边使用相同构建参数和同一初始 timing cache 的独立副本。Timing cache 保存 TensorRT 的构建计时信息，能减少部分差异，但不会冻结所有实现选择。

以往 YOLO26n 对照中，原模型重新构建也出现过与分组模型相同的 Reformat 层数减少，所以不能只凭“模型层变少”解释加速。这里保留这种区分，具体构建记录见[模型图实验报告](../benchmarks/rtx3060-grouped-topk-2026-09-14/README.md)。

## 保留分数语义，还要检查边界

[rewrite_model()](../../tools/grouped_topk.py) 只接受本仓库约定的静态 80 类、opset 16 模型，检查目标节点、输入长度、`k=300` 和排序方向。分组数必须整除两个输入长度，且每组至少有 300 项。除这两个节点外，其他节点、权重、模型 IO 和元数据保留不变；验证形状所用的常量求值不会混入最终输出模型。

分数不同的时候，正确的选择应对应相同的赢家。分数相同时，多种候选都可能满足分数上的 TopK；尤其在第 300 名附近，具体选中的索引可能受后端影响。FP16 舍入还会让原本相近的分数变成同分。因此应同时检查分数、索引和最终检测框，不能把相同分数直接当成所有检测结果相同。

```bash
.venv-export/bin/python tests/test_grouped_topk.py -v
```

这组 CPU 测试只需 ONNX 和 NumPy，覆盖唯一分数、赢家集中在一组、同分边界、索引回映射、模型保留规则及禁止覆盖文件。完整精度还需要有标签的数据集；少量样例输出一致不等于 mAP 已验证。

最后可以自己构造一个反例：把每组保留 300 改成每组保留 38，再让全局最高的 300 个分数都落在第一组。沿着两次筛选逐步推演，指出哪些候选在合并之前已经丢失，以及最后一次 TopK 为什么无法找回它们。
