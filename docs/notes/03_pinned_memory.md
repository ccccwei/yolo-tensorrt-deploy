# 03：Pinned Memory（锁页内存）

01 在 CPU 上生成模型输入，再上传 GPU 推理、下载结果并在 CPU 后处理。03 则先上传原图，由 CUDA 完成前处理，并为输入和输出准备可复用的**锁页内存**。本篇以 01 为起点，把计算位置和内存路径的变化一起讲清楚。

源码：[main.cpp](../../src/03_pinned_memory/main.cpp)、[preprocess.cu](../../src/03_pinned_memory/preprocess.cu)。基准实现见 [01 源码](../../src/01_baseline/main.cpp)。

## 先看一张图片经过哪里

假设图片是 1280 × 720，模型输入是 640 × 640。01 在 CPU 上将它缩为 640 × 360，上下各补 140 行，再转换通道顺序、除以 255，并排列成三个连续的浮点通道平面，最后上传这块模型输入。

03 上传的是三通道字节原图。GPU 上的一个线程负责一个输出像素：计算原图采样位置，用相邻四个像素插值，完成舍入、归一化和 BGR 到 RGB 的转换，直接写入模型输入的三个平面。补边位置写 `114/255`。这些操作合在同一个 GPU 函数，也就是一个 CUDA kernel 中执行，减少了中间图像的生成。

但图片由 `cv::imread()` 读进来后，还不能直接进入本版的上传路径：程序要先将它复制到一块专门准备的 CPU 缓冲区。

```text
01：CPU 前处理 → FP32 输入 H2D → TensorRT → D2H → 等待 → CPU 后处理
03：普通原图 → CPU 暂存拷贝 → 原图 H2D → CUDA 前处理 → 等待
    → TensorRT → D2H → 等待 → CPU 后处理
```

H2D 表示主机内存到显存的复制，D2H 表示显存到主机内存的复制。相对 01，03 同时改变了前处理位置、上传内容、主机缓冲区类型和同步位置；它的整体加速比不能单独当作锁页内存的收益。

## 为什么专门准备一块 CPU 内存

普通 CPU 内存的页可以由操作系统进行分页管理。传给 CUDA 复制接口时，运行时可能需要先将数据暂存到适合设备传输的内存，才能继续上传；使用 `cudaMemcpyAsync()` 也不保证这段主机侧过程完全异步。

如果提前申请一块使用期间不会被换出的内存，并反复使用，程序就能明确掌握这块传输缓冲区的生命周期。这就是 **Pinned Memory**，也叫锁页内存。本版使用 `cudaMallocHost()` 申请它。

锁页内存仍在 CPU 一侧，上传到 GPU 的复制依然存在。它支持主机和设备之间的异步传输，也为传输与计算重叠提供条件；实际能否重叠，还取决于调度和硬件。本版每张图片都执行完再处理下一张，不做跨图片并发。

以 1280 × 720 原图为例，每个请求都先把 2,764,800 字节复制到锁页暂存区，然后再上传显存。这次 CPU 拷贝本身有成本。即使测试反复使用同一张图片，也必须每次重新复制并计时，否则会省掉真实输入变化时需要完成的工作。

## 缓冲区如何反复使用

`CudaResources` 中的 `host_image` 是锁页原图暂存区，`host_output` 是锁页输出区；`image`、`input`、`output` 则在显存中。先区分这些名字，后面的读写关系就容易跟踪。

`prepare_image()` 在每张图片预热之前检查容量。新图更大时，它先等当前 stream 完成，再扩容主机和设备的原图缓冲区；新图更小时直接复用。固定大小的模型输入和输出在初始化时只分配一次，因此正式测量不包含这些分配成本。

`preprocess()` 每次先检查图片尺寸，再把当前像素复制到 `host_image`：

```cpp
if (image.isContinuous()) {
    std::memcpy(cuda.host_image, image.data, image_bytes);
} else {
    // 各行之间有空隙时，逐行复制 image.ptr(row) 的有效像素。
}
```

例如从大图截取一块 ROI，ROI 的每行末尾到下一行开头之间可能仍跨过原图的其他像素。按行复制可以只取当前图片的有效部分，暂存区内得到的原图是紧密排列的。

接着，`preprocess()` 把锁页原图上传，调用 `preprocess_cuda()` 写入 TensorRT 输入，再等待 stream 完成。stream 是 GPU 工作的有序队列；同一队列里，前处理会等上传完成后再读取原图。

`infer()` 提交 TensorRT 推理，随后直接把输出下载到 `host_output`。等待结束后，`postprocess()` 读取这块缓冲区，不需要再复制到普通浮点 vector。

这里的生命周期要求很具体：上传完成前不能改写 `host_image`，下载完成前不能读取 `host_output`，GPU 工作完成前不能释放它们。`CudaResources` 析构时先等待 stream，再释放内存；锁页内存用 `cudaFreeHost()`，显存用 `cudaFree()`，两种释放方式不能混用。

锁页资源也不宜无限增加，因为它占用系统可用的物理内存。本实现按容量复用有限的缓冲区；CPU 后处理仍会创建检测结果 vector，因此整个请求并非完全没有内存分配。

## CPU 最后得到什么

模型仍输出固定的 `[1,300,6]`，每行包含四个框坐标、分数和类别。CPU 过滤异常值与低于 0.25 的分数，用 `(坐标 - 补边) / 缩放比例` 恢复原图位置，再裁剪边界、去掉无面积框并保留候选顺序。

例如输入缩放比例为 0.5、上侧补边为 140 时，模型坐标 `y=190` 恢复为原图的 `y=100`。这一规则与 01 相同；模型、权重和后处理算法也没有改变。

前处理改到 CUDA 后，插值实现与 OpenCV 可能有一个灰度级的舍入差异，因此不应要求所有检测结果逐字节相同。像素误差测试和输入输出测试用于检查实现，完整数据集精度仍需另外评估。

## 怎样读本版的计时

`timings.csv` 每行是一条正式请求。`preprocess_ms` 包含 CPU 暂存拷贝、原图上传、CUDA 前处理和第一次等待；`infer_ms` 包含 TensorRT、输出下载和第二次等待；`postprocess_ms` 包含 CPU 检测结果处理，不含画框。

**与 01 比较时使用 `total_ms`**，也就是从前处理开始到 CPU 后处理结束的墙钟耗时。它直接测量整个请求，不能用各阶段的 P50 相加代替。`infer_ms` 也不是纯 TensorRT kernel 时间。

读图、engine 加载、缓冲区分配或扩容、预热、绘图、日志和文件写入都在正式请求计时之外。暂存拷贝在计时之内，是判断本实现实际收益时不可省去的一部分。

## 相对 01 的结果

统一实验使用 RTX 3060、YOLO26m FP16 / FP32 I/O、640 × 640、batch 1、Release；`bus.jpg` 和 `zidane.jpg` 共 3 轮，每轮每图预热 200 次、测量 1000 次，每版 6000 条请求记录。

| 版本 | 请求 P50（ms） | 相对 01 加速比 |
| --- | ---: | ---: |
| 01 · CPU 前后处理 | 4.547317 | 1.00× |
| 03 · CUDA 前处理、锁页暂存、CPU 后处理 | 3.861314 | **1.18×** |

`4.547317 ÷ 3.861314 ≈ 1.18`，表示本轮 03 的请求 P50 比 01 更低。这是上述全部变化共同作用的结果，不能说“只加锁页内存就快了 1.18 倍”。

锁页暂存增加了 CPU 拷贝，而两次同步仍保留，所以它不会自动隐藏传输时间。本表也不能单独隔离暂存拷贝、传输或 CUDA 前处理各自的贡献。[统一测试报告](../benchmarks/rtx3060-yolo26m-2026-10-15/README.md)保留条件和原始数据；结论限于本轮两张示例图的稳态请求延迟。

## 自己运行一次

先按仓库 README 准备依赖与 engine，然后在仓库根目录执行：

```bash
cmake --preset release -DCMAKE_CUDA_ARCHITECTURES=native
cmake --build --preset release --target yolo_baseline yolo_pinned_memory -j
./build/release/src/yolo_baseline weights/yolo26m.fp16.engine images 1000 200
./build/release/src/yolo_pinned_memory weights/yolo26m.fp16.engine images 1000 200
```

两版使用同一 engine、图片、每图 1000 次正式测量和 200 次预热。结果分别写入 `results/01_baseline/` 和 `results/03_pinned_memory/`，重复运行会覆盖同名输出，多轮比较时需另存每轮目录。上面的命令用于本地对照；已记录结果的 engine 哈希见统一报告。

源码入口按 `prepare_image()` → `preprocess()` → `infer()` → `postprocess()` 阅读即可。[锁页内存组件测试](../../tests/pinned_memory_test.cpp)覆盖容量复用、ROI 和输入内容变化后的再次复制。

一个具体自检是：假设两次请求之间改了原图像素，指出哪一行把新像素送入锁页区，以及最早什么时候才能安全改写这块锁页区。能解释这两个时刻，就能判断哪些复制和等待不能随意删掉。
