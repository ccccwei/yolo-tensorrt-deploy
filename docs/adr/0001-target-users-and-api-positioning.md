# ADR-0001：目标用户与 API 定位

- 状态：已接受
- 日期：2026-09-01

## 背景

`yolo_deploy` 必须先明确为谁解决问题，才能决定公共 API、依赖范围、默认行为、文档深度和性能验收方式。

面向初学者的一键式 YOLO 部署方案已经很多。若继续以“隐藏所有细节、支持尽可能多的模型”为主要目标，项目会被迫扩大模型适配、自动导出和平台兼容范围，却难以在低延迟、可控性和性能可信度上形成清晰优势。

本项目选择把精力集中在原生部署中最难被通用封装解决的问题：内存所有权、CUDA Stream、异步执行、同步边界、GPU 前后处理、尾延迟和可复现 Benchmark。

## 决策

`yolo_deploy` 的主要用户是专业的 C++ / CUDA / TensorRT 部署工程师；高级学生和希望学习 GPU 推理优化的开发者是次要用户；Python-only 初学者和只需要一键导出的用户不是首要服务对象。

一句话定位：

> `yolo_deploy` 是面向原生 C++ / CUDA 系统的轻量 YOLO 低延迟运行时，让使用者能够明确控制内存、异步执行和性能边界。

## 目标用户

主要用户通常具备以下特征：

- 能使用 CMake 和 C++ 集成第三方库；
- 理解 Host Memory、Device Memory 和 CUDA Stream 的基本概念；
- 需要把 YOLO 嵌入机器人、视频系统、原生应用或在线服务；
- 关心 Batch=1 延迟、P99、显存、稳定性和可复现性；
- 希望复用可靠的 Runtime，而不是自行维护 TensorRT Plugin 和 CUDA Kernel。

次要用户包括具备 C++ 基础、希望理解 TensorRT / CUDA 性能工程的学生和开发者。项目通过清楚的架构、实验和性能数据帮助他们学习，但不会为了隐藏专业概念而改变核心设计。

## 非目标用户

首版不以以下需求为中心：

- 只提供 `.pt` 文件，希望一条 Python 命令完成所有工作的初学者；
- 训练、调参、蒸馏或模型结构研究用户；
- 首先要求覆盖所有 YOLO 版本、任务和操作系统的用户；
- 不关心同步、内存和计时边界，只需要展示效果的 Demo 用户。

这些场景可以通过示例或外围工具提供有限帮助，但不能扩大或扭曲核心 Runtime 的职责。

## 产品原则

### 1. 核心显式，外层方便

公共接口分为两层：

- 高性能核心接口显式接收图像格式、尺寸、Pitch、Device Pointer、输出 Buffer 和 CUDA Stream；
- 便捷接口提供 Host Image 到检测结果的同步调用，用于最小示例、正确性验证和快速集成。

便捷接口必须建立在同一个核心实现之上，不能形成第二套推理逻辑。

概念接口：

```cpp
// 高性能路径：调用方控制显存、Stream 和同步时机。
Ticket Detector::enqueue(
    const DeviceImageView& image,
    DeviceDetectionsView output,
    StreamHandle stream);

// 便捷路径：库管理 Host / Device 传输并等待最终结果。
std::vector<Detection> Detector::infer(const HostImageView& image);
```

### 2. 不隐藏成本

- 异步接口不得在内部强制全局同步；
- 热路径不得隐式创建 Context、Stream 或执行逐帧内存分配；
- Host / Device 拷贝、格式转换和结果同步必须能从接口或文档中识别；
- “zero-copy”“异步”“端到端”等术语必须对应准确的执行边界；
- 默认行为必须可测量，不能依赖无法解释的自动调优或静默回退。

### 3. 窄而完整

首个可用版本优先完成一个参考 YOLO Detect 模型、固定 Shape、Batch=1 和 FP16 路径。先保证正确性、完整链路和可信性能，再增加模型、任务、动态 Shape、INT8 和多平台支持。

模型数量不是首版成功指标。首版成功意味着：用户能够理解输入输出契约、稳定集成 Runtime，并复现项目公布的正确性与延迟结果。

### 4. 核心保持轻量

- Runtime 核心只依赖 C++、CUDA 和 TensorRT；
- OpenCV、Python、Ultralytics、可视化和文件解码属于可选工具或示例；
- Runtime 消费明确契约的 ONNX / Engine，不依赖训练框架；
- 公共 API 尽量不暴露 TensorRT 类型，但不会隐藏 CUDA Stream 和设备内存等必要概念。

### 5. 优化必须有证据

每项性能优化都必须说明：

- 解决了哪个可观测瓶颈；
- 改变了哪段执行路径；
- Benchmark 的起点、终点和同步位置；
- 优化前后的 P50 / P95 / P99、显存和正确性结果；
- 在哪些硬件、输入或负载下没有收益。

不能用平均延迟的倒数冒充并发吞吐，也不能用 synthetic tensor 的 Engine 数字冒充完整图像 Pipeline 延迟。

## 文档边界

不同文档承担不同职责：

- `README.md` 面向当前用户，只写已经可用并验证过的能力、安装、最小示例、兼容矩阵和常见问题；
- `ROADMAP.md` 记录尚未完成的里程碑、验收条件和性能协议；
- `docs/architecture.md` 解释模块边界、所有权和同步模型；
- `docs/performance.md` 记录优化方法、测量口径、对照实验和适用条件；
- `docs/adr/` 保存已经做出的重要产品与架构决策。

未实现的能力、内部计划、调研过程和性能承诺不得写成 README 中的现有用户能力。

## 对首版实现的约束

开始编码时必须满足以下约束：

- 同步便捷 API 与异步核心 API 从一开始就有清楚的边界；
- 输入视图携带内存位置、格式、宽高和 Pitch，不能默认所有图像连续；
- 调用方能够控制 CUDA Stream 和最终同步时机；
- Buffer、Context 和 Stream 具有明确所有权，不使用全局可变单例；
- Builder 与 Runtime 分离，推理热路径不构建 Engine；
- 正确性参考路径可以较慢，但必须与优化路径共享同一输入输出语义；
- Benchmark 输出机器可读原始结果，而不只打印一个 FPS；
- 可选便捷功能不能成为核心库的强制依赖。

## 评审检查表

新增功能或 API 在合并前应回答：

1. 它是否解决主要目标用户的真实部署问题？
2. 它是否引入隐藏拷贝、隐藏同步或热路径分配？
3. 专业用户能否控制关键资源和执行边界？
4. 便捷封装是否仍复用同一个核心实现？
5. 是否扩大了首版模型或平台范围，却没有改善正确性和性能证据？
6. 文档描述的是已验证事实，还是尚未兑现的计划？

若一项改动主要服务非目标用户，并明显增加核心复杂度，应优先放在独立工具、示例或后续扩展中。

## 结果

这一决策会让核心接口比纯 Python 封装更显式，也要求使用者理解必要的 CUDA 概念。作为交换，项目能够提供可预测的资源所有权、真正可组合的异步执行和可信的性能边界。

项目仍会提供最小同步示例，降低首次验证成本；但“容易开始”不能以牺牲专业用户的控制能力为代价。
